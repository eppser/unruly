# Auditing unruly

This document is for somebody who did not write this code and has no reason to
trust it. It says what each check establishes, what would falsify it, and where
the claims are weakest.

## Run everything

```sh
make audit                    # everything this machine can run
make audit-offline            # only what needs no Docker and no credentials
scripts/audit.sh --out r.md   # also write the report to a file
```

Exit codes mirror the scanner's own contract, on purpose:

| code | meaning |
|---|---|
| 0 | every check ran and passed |
| 1 | a check failed |
| 3 | everything that ran passed, but some checks could not run |

**Those are `scripts/audit.sh`'s codes, not `make`'s.** GNU make exits 2 for any
failed recipe, so `make audit` collapses 1 and 3 into the same number and the
distinction this table exists for — a check that FAILED versus a check that
could not run — is lost. Measured in a fresh clone: the script exits 3, `make
audit-offline` exits 2 for the same run. The true code is printed on the last
line of the summary either way (`8 passed, 0 failed, 16 not run (exit 3)`), but
anything gating on `$?` should call the script directly.

**A row marked _not run_ is not a pass.** That distinction is the entire thesis
of the tool, and it is applied here to the tool's own test suite because this
repository has broken it twice from the inside: every `make eval-*` once passed
from cache without executing anything, and a dead Docker daemon has repeatedly
produced recall figures that described the harness rather than the scanner
("read-exposure-classifier is UNSOUND", "probed 9 relations in 3ms").

### How long it takes

The offline half is fast; the whole thing is not, and an auditor should plan
for that rather than discover it.

| stage | roughly |
|---|---|
| offline (`make audit-offline`) | 20–30 min on this machine; the 208-mutation sweep is about 20 min |
| fixtures | 5–10 min, plus first-run image pulls |
| live | 2–3 min |

`make audit` exceeds a ten-minute window on this machine, so run it detached
rather than waiting on it interactively.

### As part of the loop

This project is developed in a loop that makes a change, runs the evals and
commits. `make audit` is the same set of checks that loop runs, in one command
with a report, so the state an auditor reproduces is the state each iteration
is held to — not a separate ceremonial suite that drifts away from what is
actually run.

`docs/audit-report.md` is the last report generated by `make audit`, and it
names the commit it describes. If that commit is not `HEAD`, the report is
stale and the number to trust is the one you produce by running it yourself.

That sentence was true and useless for most of this project's life. `make
audit` wrote `./audit-report.md`, and `.gitignore` carried `audit-report.md`
as a bare pattern, which git matches at ANY depth -- so the file this document
points at was ignored, untracked, and absent from every clone, while the
staleness check it describes would have said "stale" forever. Both are fixed:
the pattern is anchored to the repository root, `make audit` writes here, and
the report is committed.

## What each check establishes

### Offline — no Docker, no credentials, runnable by a fork

| check | establishes | how to falsify it |
|---|---|---|
| `build` `vet` `lint` | the tree compiles and is gofmt-clean | edit a file badly |
| `unit` | every package's tests pass | — |
| `race` | no data races under `-race` | — |
| `mutation` | **each decision the scanner makes is checked by some test** | add a mutation to `scripts/mutate.py` that breaks a real decision; if the suite stays green, that decision is unverified |
| `coverage` | every finding id has an emit site the offline suite executes | delete a test and re-run; the id it covered should appear as uncovered |

`mutation` is the one worth your attention. Its 208 mutations each break one
decision. Coverage says a line ran; mutation
says a test would notice if the line were wrong. It has found five unchecked
decisions so far, including whether the write probe actually deletes the row it
creates, and whether a scan that could not see still exits 3.

### Fixtures — needs Docker, still no credentials

Five compose projects: a deliberately vulnerable PostgREST, a correctly
hardened one, a policy matrix, the real Deno edge-runtime, and three hosts that
are not Supabase at all.

| check | establishes |
|---|---|
| `eval-pocketbase` | recall and precision against a deliberately vulnerable PocketBase and a hardened one, plus a cross-check that an independent implementation — importing nothing from the scanner — retrieves what the scanner reports and retrieves nothing from what it stays quiet about. Including the two answers that look like findings and are not: a 200 with zero rows and a 404 on a fake id. The third -- a 204 from a realtime subscribe -- is measured in docs/pocketbase-ground-truth.md but the surface is not probed, so it is declared under the provider's Cannot() rather than counted here |
| `eval-neon` | The Neon backend agrees with its committed answer key. Replays a transcript recorded from the live Data API, so it needs no credential and no quota. Grades recall (the RLS-disabled table is reported), precision (the three protected tables are not, including the one Neon's own console falsely flags), and refuses to run on an answer key that parsed to nothing. | `make eval-neon` |
| `eval-neon-live` | Two implementations against the real Neon Data API. `internal/exploit/neon.go` rewrites the Neon Auth sequence from scratch and imports nothing from the scanner, so its agreement corroborates the measurement rather than repeating it. Requires them to agree on the rows retrieved AND on the three tables that must stay silent -- including the one Neon's own console falsely flags. Read-only: the fixture's seed row counts are untouched. Skipped with its reason when `.secrets/neon.env` is absent. | `make eval-neon-live` |
| `eval-neon-binary` | Builds the scanner and runs it against the Neon lab as an operator would, then requires exit 2 and the escalation in the report. It exists because four defects reached main while every stage-level eval stayed green -- the backend unreachable from a target URL, the target never offered to the detector, serial probing that never finished, and stages pointed at the database root instead of the REST prefix. That last one is unreachable by replay: the recorded transcript's paths cancelled out the prefix that was wrong. | `make eval-neon-binary` |
| `eval-fixtures` | recall against known-vulnerable, precision against known-hardened |
| `eval-exitcode` | 0 clean / 2 findings / 3 could-not-measure |
| `eval-notsupabase` | near-silence against an SPA, a deny-all host and a catch-all |
| `eval-edge` | Edge Function classification against the real runtime |
| `eval-redaction` | `-redact` removes sampled data and keeps the finding usable |
| `eval-templates` | the worked SQL inside every `-fix` actually executes |
| `eval-determinism` | repeated identical scans produce byte-identical reports |
| `eval-exploit-local` | an independent implementation exploits the fixture, and the scan agrees with what it could and could not do |
| `eval-remediation` | applying the tool's own `-fix` output closes the findings |

The hardened fixture is the interesting one: it holds real data in relations
that are reachable and correctly protected, so a scanner with broken logic has
something to get wrong. Its expectation is "nothing above LOW" rather than
zero, and the one low is honest — PostgREST builds its fuzzy-match hint from
the schema cache, which knows nothing about privileges, so an internal
routine's name leaks even with `EXECUTE` revoked. No database configuration
suppresses it.

### Live — needs the exploit lab

A real Supabase project plus a Cloudflare Worker, with an answer key. Not
runnable without credentials, which are gitignored.

| check | establishes |
|---|---|
| `exploitcheck` | every vulnerability in the answer key is genuinely exploitable, with retrieved data as proof |
| `eval-exploitability` | everything reported at high+ is exploitable, and everything exploitable is reported |
| `eval-noresidue` | `-no-residue` writes nothing to a REAL project — rows and objects counted past RLS with the service key, before and after — while still reporting the write exposure |

The exploit harness in `internal/exploit` imports nothing from the scanner's
probe or surface packages — verify with `go list -deps`. Agreement between them
is only meaningful because they cannot share a wrong assumption.

## Running it without the lab credentials

Five of the twenty-four checks talk to a cloud project whose keys live in
`.secrets/`, which is gitignored. Anyone cloning this repository has the other
nineteen and cannot run those five.

Measured, by cloning this repository the way a fork receives it — `.secrets/`
is gitignored, so a clone never has it — and running the gate with Docker
available:

```
19 passed, 0 failed, 5 not run (exit 3)

exploitcheck          not run — lab credentials absent (.secrets/ is gitignored)
eval-exploitability   not run — lab credentials absent (.secrets/ is gitignored)
eval-graphql          not run — lab credentials absent (.secrets/ is gitignored)
eval-noresidue        not run — lab credentials absent (.secrets/ is gitignored)
eval-exploit-firebase not run — lab credentials absent (.secrets/ is gitignored)
```

Two things about that output matter more than the number.

**It is not green.** Exit 3 is could-not-measure, and the report says _not run_
rather than counting the five as passes. That is the same rule the scanner
applies to a target: absence of a finding is only evidence when the scan could
see. A harness that reported 19/19 here would be making exactly the claim this
project exists to stop making.

**It names the reason.** Each row says which credential is missing, so a
contributor knows what they are not covering rather than discovering it when
something breaks.

The five are the remaining reach of the cloud lab. Auth and Storage used to be
in this set and are not any more: they were moved to local fixtures (a real
GoTrue, and the storage responses served by the gateway), which is the whole
argument for building those fixtures. `eval-exploitability` is the one worth
moving next, because it carries the only end-to-end grading of the Realtime
delivery probe — the package's own tests cover the protocol thoroughly, but the
wiring from `main.go` is graded only there.

## Reproducing the fixtures

```sh
make fixtures-up      # starts all five, waits for each to answer
make fixtures-check   # fails loudly if any is not serving
make fixtures-down
```

Images are pinned BY DIGEST in each `docker-compose.yml`, and every image is
recorded in the audit report so a later run can tell drift from disagreement.

Two of them were floating (`nginx:alpine`, `jmalloc/echo-server:latest`) until
the audit report listed them and made it obvious. A floating tag makes a
fixture reproducible only until the upstream image moves, and an eval whose
target silently changed measures two different things and reports one number.

## Where these claims are weakest

Stated plainly, because an audit that only lists strengths is marketing.

**The list of skippable checks is curated, not derived.**
`unruly-checks-skipped` is how this scanner says "I did not look at this, and
here is the flag that would make me". Fourteen checks declare themselves there
and each has a test asserting it appears under the right condition and vanishes
under the right flag.

**Completeness is now checked too, and it found two more.** The objection
recorded here was that a completeness guard "has to enumerate every stage and
every input-conditional early return... that is a registry, and a registry is
what already exists and already drifted". True of a hand-written list; not true
of one derived from the code. `TestEveryStageThatCanDeclineIsAccountedFor`
reads every stage's `Run` method and matches a narrow shape: an opening guard
that returns nil because its own configuration is empty. That is a stage saying
"nothing was supplied, so I did nothing" — indistinguishable, in a report, from
"looked, found nothing". Later returns are not matched, because those follow
work, and work that found nothing is a real result.

On its first run it named `routes` and `subdomains`. `application-routes` was
disclosed only when the operator passed `-no-routes`; naming no `-site` at all
silenced the identical check in silence. Subdomain enumeration had no entry
anywhere. Both are now declared, with tests in both directions.

The enumeration cannot drift, because it is read from the stages. What can
drift is the ACCOUNT — the map from a declining stage to the entry that
discloses it — and that is a build failure: a new declining stage, a renamed
entry, or a stage that stops declining each fail it, verified by doing all
three.

### Exit 3 is could-not-measure, all the way up

The scanner uses exit 3 for "I could not look", and `eval-exitcode` grades it.
`cmd/exploitcheck` now returns it too, when a lab has drifted from its answer
key or run out of quota — and `scripts/audit.sh` renders it as _not run_ rather
than FAIL.

Without that last step the chain broke at the top: the exploit runners were
taught to distinguish a changed laboratory from a refuted exploit, and the
audit turned every nonzero status back into "this check failed", blaming the
scanner for the lab. A red audit sends someone hunting a regression that is not
there, which costs exactly what a false pass costs.

`TestAuditSeparatesCouldNotMeasureFromFailed` lifts `run()` out of the script
and exercises three exit codes: 3 is not run, 1 is still FAIL, 0 is still pass.
The middle case is the one that matters — a check asserting only that drift
skips would be satisfied by a branch that skips everything, and that was
verified by making the branch greedy and watching the genuine failure stop
failing.

### The commit gate, and why it is deliberately weak

`scripts/githooks/pre-commit` refuses a commit that is not gofmt'd, does not
build, fails `go vet`, or breaks one of the fast structural guards. Enable it
with

    git config core.hooksPath scripts/githooks

Twice in one week a commit landed on a red tree here. Both times the suite had
been run and the failure had been PRINTED: once the command was
`go test ...; git commit` rather than `&&`, once the output scrolled past.
Reading a result is not the same as depending on one, and the difference is
invisible until it costs something.

It runs in about two seconds, and that is a design constraint rather than a
happy accident. The full suite is over two minutes and the audit is
twenty-five; a hook that slow gets `--no-verify` within a day, and a gate
people route around is worse than no gate, because it also removes the habit of
checking by hand. So it runs what is cheap and catches the shape that actually
got through -- a compile error, an unformatted file, or a structural guard that
grades the tree against its own documentation. That last set is what caught the
most recent red commit: a finding using a protocol absent from
`finding.KnownProtocols`.

`--no-verify` still works, on purpose. This project commits failing tests
deliberately and often -- watch it go red first is the whole method -- and a
gate that forbade that would be fighting the practice it exists to protect.

### Breaking a check on purpose, without fooling yourself

`scripts/verify-break.sh PACKAGE PATTERN FILE 'OLD' 'NEW'` applies one edit,
confirms the package still builds, runs the named tests, and says CAUGHT or
SURVIVED. It refuses rather than answering when the question was never put.

The build check is the reason it exists. Three times in one week a break was
applied by hand, `go test` reported zero failures, and that was read as "the
guard does not catch this" -- when the edit had left a variable unused, the
package had not compiled, and no test had run. **Zero failures and a clean pass
are the same number.** `scripts/mutate.py` already carried this lesson in
`--buildcheck`, on the same reasoning; it just was not available to a break
typed during development, which is where it kept happening.

Three refusals, each a way of getting a confident answer to a question nobody
asked:

- the text to replace appears zero times, or more than once
- the edit does not compile
- the pattern matches no test

Its own first version had the third defect. `go test` prints `ok ... [no tests
to run]` for a pattern matching nothing, and the script counted that as a run
and reported SURVIVED -- the exact conflation of "measured and fine" with
"never asked" it was written to prevent. It counts `=== RUN` lines now.

SURVIVED is an answer, not an error: it means the behaviour is genuinely
unguarded, which is worth knowing. Only a refusal exits non-zero.

### A fixture that mis-records is worse than a fixture that fails

`go test -race` found an unsynchronised `append` in the Neon enumeration
fixture. The handler recorded every probed path into a captured
slice; net/http serves each connection on its own goroutine; the stage probes
concurrently by design. `go test` had passed. The race detector is dynamic, so
it reported the overlap only because the scheduler happened to produce one on
that run.

The interesting part is not the race, it is what a race in a fixture does. A
recorder that drops entries does not make a test fail — it makes the test
assert about evidence that was never collected, and pass. For a scanner whose
entire claim is "the evidence is real", a fixture that quietly mis-records what
was sent undermines every assertion downstream of it. Measured directly: with
the lock removed, the recorder kept **150 of 200** requests.

The same class had been found here before, in `internal/enumerate`, where a
comment still records a `throttled++` that went "undetected for a long time".
It was fixed where it was found, and recurred anyway. So the guard is now
structural: `TestNoTestHandlerMutatesCapturedStateUnlocked` parses every
`_test.go` in the tree, finds func literals with an `http.Handler` signature,
and fails on any assignment or increment whose target is declared outside the
literal, unless the body takes a lock or uses sync/atomic. It found **18**
sites on first run, across ten packages, in fixtures written over the life of
the project.

`internal/testrec` exists so the fix is cheaper than the defect: a
concurrency-safe `Log` whose zero value is usable. It records rather than
counts on purpose — a bool says something happened, a log says what happened,
which is the difference between a fixture that can confirm its own expectation
and one that can show you the request it objected to.

The check is syntactic and its gaps are in the direction of false negatives:
it does not see mutation through a method call, and a captured name shadowed
later in the same handler is read as local.

### The mutation build-check no longer edits the tree it is checking

`--buildcheck` verifies that every mutation still COMPILES, because a mutation
with a syntax error is scored caught forever while testing nothing. It is
spawned by a Go test, which means it runs inside `go test ./...` alongside
every other package's compilation -- and it used to apply each mutation to the
working tree. Measured: **53 source files** modified during a single test run.

Any other package compiled during one of those windows is built from a mutated
dependency and can fail for a reason that has nothing to do with it, then pass
on the next run. That happened: `cmd/unruly`'s `TestChooseKey` failed with the
exact three symptoms of the `chooseKey` mutation. A `go test ./...` had been
killed at its timeout, and killing the parent does not kill the child, so an
orphaned mutate.py went on cycling mutations with nothing waiting on it.

mutate.py restores correctly on SIGTERM -- it installs handlers for INT, TERM
and HUP. The hazard was never a failed cleanup; it was that the file is mutated
at all while other processes are reading it.

`--buildcheck` now copies every tracked file (working-tree content, so
uncommitted edits are still checked and .gitignored material is never copied)
into a temp directory and builds the mutations there. Same 133 mutations, same
~23s, and the tree stays clean -- verified by the check itself, which samples
`git status` while the child runs and fails if the dirty set grows. A killed
run now abandons a temp copy instead of a source file.

The FULL mutation run still rewrites the working tree, by design: it runs the
test suite against mutated code. That is why the audit runs it as its own
stage, and why killing an audit mid-mutation still needs `git status` checked
afterwards.

**The benchmark's numbers are re-run deliberately; the CLAIM is gated.**
`make benchmark` brings up fourteen docker stacks and takes minutes, so it is
not an audit stage -- a check nobody can afford to run is a check that gets
turned off. What the audit does enforce, in
`TestTheAccuracyClaimMatchesTheMeasurement`, is that the README never says more
than the last measurement did: every corpus project is either scored in
`benchmark/RESULTS.md` or listed as not scored WITH A REASON, every percentage
the README quotes matches the scoreboard's totals, the stated counts match the
corpus, and the scoreboard names a commit that exists. Staleness is reported
rather than failed -- the check logs how many commits and score-affecting files
have landed since the measurement, currently 28 and 51.

It found real drift on its first run: the README claimed a corpus of fourteen
projects scoring thirteen, when the corpus holds fifteen and fourteen are
scored. `15-grant-vs-rls` -- the datapoint where grant-aware detection beats
Neon's own console -- had been added without the claim being updated.

Every arm was verified by breaking it: wrong corpus size, inflated recall, a
doctored precision figure, a commit not in the repository, and a corpus project
added but never scored. The precision arm was inert on first attempt, written
as `if readme contains "100% precision on every"` -- a literal that stopped
matching when the sentence wrapped across a line, so it passed a scoreboard
doctored to 71.4% without a word. It is a required pattern now: a claim this
central should not be able to stop being checked by being reworded.

It is not merely an oversight that it sits outside. The benchmark exits non-zero
whenever recall is imperfect, and recall IS imperfect: 09-huge-schema hides
relations behind names no vocabulary can reach (`kv_089941`, `t1`), and
07-rewriting-proxy and 13-rpc-security-definer each miss one name. Those gaps
are honest and known. Wiring a strict scoreboard into a pass/fail gate would
mean either freezing today's recall as a floor -- which turns a measurement into
a ratchet nobody may lower even when a fixture changes -- or softening it until
it passes, which is worse. Neither is obviously right, so the state is recorded
here rather than resolved silently.

What the benchmark establishes, and what would falsify it: precision is 100% on
every dimension across 15 projects (42 protected relations, 50 read exposures,
93 relations, 6 routines, 8 escalations, 6 writes). A single false positive
anywhere falsifies the central claim, because the argument against the vendor
consoles is that grant-aware detection reports FEWER wrong things, not more
things. 15-grant-vs-rls is the datapoint that names a console directly: Neon's
own console warns that a table with RLS disabled lets all authenticated users
read every row, which is false where no role holds a GRANT.

One project is deliberately non-deterministic. 08-rate-limited runs nginx
limit_req at 5r/s over a real PostgREST, so which relation goes unmeasured
varies between runs -- payment_cards one time, user_credentials the next. Both
score n/a and no total moves. That is the fixture working, and it is documented
in its own README; it is not a determinism regression in the scanner, whose
probe order is sorted and stable.

**The mutation set is hand-written.** 214 mutations, chosen to cover
the decisions that matter and to replay bugs this project actually shipped. It
is not exhaustive and does not claim to be. A decision nobody thought to mutate
is a decision nobody has verified.

**A mutation can be "caught" by something other than a test, and that is the
same lie one level up.** Two ways this has happened here, both found and both
fixed:

*Killed by the compiler.* run_suite scores a mutation as caught whenever
`go test` exits non-zero, and a build failure does exactly that. Six mutations
did not compile -- one had left an unmatched paren since the day it was
written, four fell foul of Go's unused-variable rule -- so they reported caught
on every audit while never reaching a test. `mutate.py --buildcheck` now
applies each mutation and builds it, and `TestEveryMutationCompiles` runs that.

*Killed by the harness's own bookkeeping.* `--check` verifies every mutation's
pattern still applies, and under a mutation the tree is deliberately wrong: the
applied mutation has replaced its own pattern, so `--check` reports it missing
and fails. For the mutations scoped to `./internal/eval/`, that meta-test was
answering for the whole suite. Both meta-tests now skip when `mutate.py` sets
`UNRULY_MUTATION_ACTIVE`; the audit still runs them in its `unit` stage, on a
clean tree, which is the only state where they mean anything.

Re-grading the thirteen affected mutations with real tests deciding: twelve
were genuinely caught, and one -- `repeated-stage-loses-a-control` -- SURVIVED.
It drops `-no-residue` from the per-schema probe, so a scan promising to create
nothing would leave rows behind in every schema but the default. That promise
had never been tested by anything; the eval that would notice needs the live
lab and skips offline. It has an offline test now.

That last sentence is not hypothetical. Because the set is curated rather than
a glob, the packages added by the multi-backend rebuild -- backend/ and scan/ --
had no entries at all, and the mutation stage passed without ever mutating
them. Passing said nothing about that code. Three entries were added to cover
the decisions those packages actually make, two of them replaying claims this
project got wrong about PocketBase and had to retract: reading exposure from a
status code rather than from rows returned, and reading permission from a 404
that an expression rule produces just as readily as an open one.

**Emit-site coverage is weaker than it sounds.** It proves the code that builds
a finding runs under test, not that a scan can reach it. A unit test calling a
constructor covers the site either way — which happened here, and was found by
deleting the constructor call and watching the site reappear as uncovered. The
fixture and exploitability evals are what establish reachability.

**Measurements in comments are measurements, not guarantees.** Constants like
the concurrency default, and behaviours like "PostgREST serves GET in a
read-only transaction" or "pg_graphql introspection is disabled", were measured
against Supabase as it was when the comment was written, and a vendor can
change any of them under you. `make saturation` re-runs
the concurrency measurement against a project you own.

### Recovering a dead Docker daemon

A check that fails because the environment disappeared is retried once, after
restarting the fixtures. That only helps if the daemon is still alive; when the
daemon itself is gone, tell the audit how to bring it back:

```sh
UNRULY_DOCKER_RESTART='colima stop -p lab; colima start -p lab' make audit
```

Unset, no restart is attempted — correct for CI, where a dead daemon is a real
failure of the runner rather than local flakiness. The retry happens only after
an ENVIRONMENT failure, never after a check that failed on its merits, and the
report says which checks were retried: an audit that quietly retries until it
is green is not an audit.

**The last fixture check is the one you are most likely to lose.** In four
consecutive full runs `eval-remediation` came back _not run (fixture became
unreachable mid-run)_ because it runs last, by which point the VM has been
under load longest. Run in isolation it passes, so nothing is hiding behind
that repeated skip -- but do not read a run where it is missing as a run where
it succeeded.

**The audit's own environment is unstable here.** The Docker VM on this machine
has died fourteen times during development, twice mid-audit. A check whose
fixture disappears underneath it is reclassified as _not run_ rather than
FAIL — the log signature is specific to the fixture guard, so a genuine recall
regression or an unexpected finding still reports as a failure. If you see
_not run (fixture became unreachable mid-run)_, that check needs re-running,
not interpreting.

**One cloud project.** The exploit lab is a single Supabase instance in one
region on one plan. Cloud behaviour that varies by plan or region is not
covered.

**The scanner cannot prove a negative.** Findings it does not report may be
absent, or may be beyond what it probes. Anything it could not measure is
reported explicitly — `unruly-surface-not-assessed`,
`unruly-capability-degraded`, `unruly-checks-skipped` — and drives
exit 3. If you see exit 0 with no coverage findings, the scan claims it looked
everywhere it knows how to look.

## Which findings have been seen in a real scan

Every documented finding id was swept against every available target -- five
fixtures, two cloud projects, a not-Supabase host -- and eleven had never been
produced by anything except a unit test calling their constructor. A rule
nobody has watched work is not a rule anybody should trust.

Nine now fire against a fixture built for them, and building those found three
real defects: an explicit `-site` silently discarded so the tool's clearest
critical could never be reported, an object-residue finding that fired only in
the rare case, and a fixture minter whose `--sub` flag parsed and did nothing.

Two remain unreachable, and that is now measured rather than assumed:

| id | why it never fires |
|---|---|
| `supabase-graphql-rls-bypass` | pg_graphql builds its schema per role from privileges AND enforces RLS, so it is equal or more restrictive than REST. `make eval-graphql` measures this and fails if it stops being true. |
| `supabase-realtime-anon-subscription` | Supabase acknowledges subscriptions for relations that do not exist, so an acknowledgement proves nothing and the check cannot discriminate. |

Both are kept: each costs little and would catch a regression upstream. The
difference is that their silence is now a finding of its own rather than an
untested belief.

### What fires against the open internet

Fixtures are built to make a rule fire. That is their job, and it is also their
limitation: a rule can pass its fixture and still never occur in the wild, or
occur constantly and never have been seen here.

So the scanner was run over 200 real third-party sites -- 100 sampled from a
list of Supabase-backed applications, 100 drawn at random from the Tranco top
1M as a control -- in `-measure` mode, read-only, no writes and no invocation.
Thirteen ids were produced:

| id | occurrences |
|---|---|
| `supabase-anon-read-exposed` | 382 |
| `unruly-surface-not-assessed` | 157 |
| `unruly-probe-budget-exhausted` | 128 |
| `unruly-checks-skipped` | 62 |
| `supabase-open-signup` | 54 |

`supabase-preview-deployment-key` had never been seen outside a fixture built
for it. It fires on real deployments.

The rest of the catalogue did not fire, and the two reasons are different:

- **Could not fire in this configuration.** Everything gated behind `-write`,
  `-invoke`, `-history` or GraphQL: write exposure, storage writes, Realtime
  delivery, Edge Functions, routine callability, historic keys. A study over
  other people's infrastructure does not get to enable those.
- **Could have fired and did not.** `supabase-service-key-exposed`,
  `supabase-db-connection-string-exposed` and
  `supabase-management-token-exposed` were all live and found nothing across
  200 sites. Those detectors remain exercised only by tests. That is a fact
  about the sample, not evidence they are wrong -- but it is the honest status,
  and it is what "never seen in the wild" looks like when somebody actually
  went and looked.

## Adversarial checks worth running

1. **Point it at a host that is not Supabase.** It should be near-silent.
   `make eval-notsupabase` does this, but try your own.
2. **Point it at an unreachable address.** It must exit 3, not 0.
3. **Send it something small and expensive.** Two shapes are covered:
   a gzip bomb, and 800 KB of 400,000-deep nested JSON. Both are well inside
   the size caps, and both would be a hostile target choosing how much memory
   or stack the scan uses. `go test ./internal/client -run "GzipBomb|ReadBody|
   DeeplyNested"`. The nesting protection is the standard library's --
   encoding/json refuses past a maximum depth -- so the test exists to notice
   if that dependency is ever swapped out.

4. **Send it a gzip bomb specifically.** Everything the scanner reads goes through a
   bounded reader, because Go decompresses transparently and a few hundred
   kilobytes on the wire can become gigabytes in memory. `go test
   ./internal/client -run GzipBomb` serves 261 KB that expands to 256 MB and
   asserts the scan keeps at most 1 MB of it, on both the credential-bearing
   client and the ReadBody path that fetches a target's own pages.
5. **Break an oracle deliberately** — block `/rest/v1/` at a proxy — and
   confirm the scan reports degraded capability rather than a clean result.
6. **Check a finding's proof.** Every finding at high or above that concerns
   the target carries something RETRIEVED from it — sampled rows for a
   relation, a response body for an application route, a truncated key prefix
   for a leaked credential — plus the `curl` in `evidence.request` that
   produced it. Re-run that command yourself; `make eval-fixtures` asserts both
   halves, and the request was missing from the critical service-key finding
   until the assertion was written.

   `unruly-*` findings are exempt and describe the scan rather than the
   target: a probe row left behind, a surface not assessed. There is nothing to
   sample from those.
7. **Check that `-fix` output is real SQL.** `make eval-templates` executes it;
   read it too.
